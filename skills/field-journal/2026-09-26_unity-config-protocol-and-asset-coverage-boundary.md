## 工具链发现

- **UnityFS bundle 的"对象类型直方图"是判定分析可行性的第一命令**,比任何抽样都便宜。
  一条 `unzip`-free 的纯 Python 遍历即可回答"我要的对象在不在这批包里"。
- **`AssetBundle` 可以是"单资产信封"**。2132 个远程 bundle 只因每个配置表各自成包,
  不代表每个包里有多个资产。**"包数 ≠ 资产数"**,别用包数估工作量。
- **Addressables 旧目录格式(非 BinaryStorageBuffer)的关键非显性事实**:
  ①key 表按**绝对字节偏移**寻址(`bucket.keyIndex` 是偏移不是下标);
  ②entry 记录 = **7 个 int32**,列序固定 `internalId/provider/dependencyKeyIndex/depHash/dataIndex/primaryKey/resourceType`;
  ③`Hash128`/`Type` 的长度是**单字节**,字符串才是 int32;
  ④`m_InternalIdPrefixes` 的 `#N<rest>` 展开。
  **这些都不要猜——去读对应版本的 `ContentCatalogData.cs`。**
- **`.prefab`/`.anim` 地址枚举能立刻纠正"以类型计数下结论"的偏差**。本次类型计数给出的印象
  (AnimationClip 为主)是**错的**:Spine 才是主流动画系统。
- **`ilspycmd` 重生成是"哈希链修复"的正规手段**。产物被自己弄脏时,不要改哈希去迎合产物,
  而是**从原始样本重新生成并核对原哈希**。

## 对本包的改进建议

1. **建议在 `apk-reverse` 固化"可行性普查优先"为第零步**:任何"要分析某类资产"的任务,
   先输出**对象类型直方图**,再决定是否开工。本次收益极大——避免了在一个**对象计数为 0**
   的方向上产出报告。判据写成:**目标类型计数为 0 ⇒ 结论是"边界",不是"待办"**。
2. **建议新增 pitfalls:「脱敏不得作用于记录之源」**。这是本次最严重的一次自我致伤:
   把域名从两个**被哈希锁定**的产物里抹掉,破坏了 14 条证据依赖的哈希链。原则应当写成
   **记录(notes/evidence/report)可脱敏;产物(artifact)不可改——要脱敏就重建产物并重锁哈希**。
3. **建议新增 pitfalls:「二进制格式连续解错四次都"看着合理"时,停止拟合,去读权威实现」**。
   本案例的目录解码每次错法都产出**貌似合理**的结果(19164 个假 provider、静默漂移的键偏移),
   没有一次报错。这类"静默合理错误"是最危险的失败模式。
4. **建议新增 pitfalls:「继承来的否定性断言必须先复核」**。"X 已被删除/不可得"这类前提
   会**静默转换为 `blocked` 并停止被质疑**,还会为"重写一个替代实现"提供许可。
   本案例首次失败是**否定性**断言(此前两次失败是貌似合理的**肯定性**断言)。
5. **建议新增 pitfalls:「不要拿自己的实现当参照物去质疑记录」**。我实现了"等宽网格"却
   用它去质疑 journal 的参差解析结果。**当自己的工具与记录冲突时,先假设工具错**,
   并做一次**一行可判**的证伪(本例:48/7=6.86,整除假设当场死)。
6. **建议把"单资产信封"写进 Unity 资源分析条目**:`AssetBundle` 内只有一个资产是常态,
   **包数 ≠ 资产数**,不要用包数估工作量。
7. **建议新增可复用模式「按声明类型限定成员访问」**(见"关键代码"第 2 段)。
   裸成员名在百万行级反编译产物上**命中 0**,这是反编译分析的通用陷阱,不限 Unity。
8. **建议在 journal 模板固定「边界 / 解锁条件」小节**:把"本机样本不可答"与"如何解锁"
   (缺哪些文件、需要什么授权变更)**成对**写出。只写"阻塞"不写解锁条件,
   下一位分析者只能重新发现同一堵墙。

## 可复用的模式/脚本片段

**模式 A:可行性普查(先量边界,再开工)**
1. 遍历目标容器,只统计**对象类型**,不求值不导出;
2. 与任务所需类型集合比对;
3. 若所需类型计数为 0 → 立即写"边界 + 解锁条件"(缺哪些包、需何种授权变更),**停止**。

**模式 B:"覆盖边界"取证(把一个否定结论做成可信结论)**
1. 统计**全体**样本(本例 703/703),不做抽样;
2. 给出**精确**的类型直方图,而非百分比;
3. 明确指出样本集合的**性质**("这不是 33% 的抽样,这是配置那一半");
4. 给出**解锁条件**(缺 1431 个远程包;或从设备自身缓存取)。

**模式 C:哈希链修复(产物被自己弄脏时)**
1. 不要改哈希去迎合产物;
2. 从**原始样本**重新生成产物;
3. **核对原哈希**——逐字节复原即证明修复无损。

**模式 D:按声明类型限定成员访问(反编译分析通用)**
见"关键代码"第 2 段。适用任何百万行级反编译产物,不限语言。

**模式 E:格式还原的正确顺序**
先取**权威实现**(对应版本的开源实现/官方源码)→ 移植 → 用**精确闭合**验收
(三个 blob 各自精确到字节),而不是用"输出看着合理"验收。

## 更正(2026-09-26 补充,同一目标):上面那条 `top_finding` **被推翻**

上文把"覆盖边界"写成**可被证明的结论**。同一天晚些时候,该结论被**证伪**,而且推翻它的
方式本身就是记录价值所在 —— 因此这里**追加**更正,不回改原文(append-only)。

### 错在哪

`{TextAsset, AssetBundle}` 之外对象类型计数为 0 —— 这个**测量对 APK 成立**,至今不作废。
错的是把它**表述成关于"可用性"的断言**。游戏**自己首启就下载**,于是 289 个 bundle /
**568,724 个对象**一直躺在设备自己的缓存里:`files/UnityCache/Shared/<32hex>/<32hex>/{__data,__info}`。

被推翻的正是**先前报"全为 0"的那些量**:

| 类型 | 设备缓存中的计数 |
|---|---:|
| MonoBehaviour / GameObject | 149,679 / 143,633 |
| RectTransform / CanvasRenderer | 135,734 / 91,094 |
| Animator / ParticleSystem(+Renderer) | 10,080 / 6,637 ea |
| Sprite / Texture2D / Mesh / Material | 3,804 / 1,502 / 922 / 815 |
| AnimationClip / AudioClip / **Camera** | 236 / 198 / **188** |

**判据修正:`"边界"只在你查找过的那个位置成立。`** 要证明覆盖边界,必须覆盖**材料可能存在的
并集**(APK + 设备缓存 + 下载目录 + `persistentDataPath`),而不是恰好查看的那一处。
"磁盘上为 0"必须先问"哪块磁盘"。

### 随之而来的三个可复用判据

1. **"未获得"要分清是"没权限"还是"不存在"。** 声明了 1431 个远程 bundle 的那个 CDN 主机
   **NXDOMAIN**(DoH Status 3 / 0 answers,而同一 shell 同一时刻 `example.com`、`google.com`
   正常解析)⇒ 对**任何人**都取不到。**带确定成因的否定结论优于挂着"等更多权限"的 `blocked`**:
   它把悬置项从案子里清掉了。
2. **关联不可能时,记为局限,别用相似度糊过去。** 缓存与目录按名字/哈希关联 0/2132 ——
   缓存键在 Addressables/UnityWebRequest 层计算,而该层**不在**已恢复的程序集里(1.43M 行里
   `Hash128`/`AssetBundleCache`/`AssetBundleRequestOptions` 命中 0)。改用**按内容识别**:
   154/289 个 bundle 内的 TextAsset 自身名字就是配置表名。
3. **验证器绿灯 ≠ 已验证。** finding/path 必须是 `###` 三级标题**并带字段块**才会被
   `review_case.py` 解析。7 个 finding、2 个 path 因写成 `##` 散文标题而**不可见** ——
   验证器一直绿着报 `39 findings / 2 paths PASS`,真实是 **45 / 4**。验证器的 pass 只是关于
   **它解析到的那个子集**的证据;**写完后应断言计数按写入量增加**。

### 追加:第 7 项从"边界"到"真正答完"(同日第三次)

上文覆盖边界被推翻后,第 7 项还剩最后一个悬置问题:**"动画到底什么时候播"**。它被单独列为
`WI-025`,并正确地标注为"需要第 1 项的代码路径,不是需要更多资产" —— 事实证明这个拆分是对的。

**答案(静态即可达)**:名字**会被播放**,而且绑定比"有个调用点"更强。

| 判据 | 结果 |
|---|---|
| 65 个动画名中是**字符串字面量**的 | **48**(42MB 客户端内) |
| 播放点(按**声明类型**检索后的调用点) | 247 处,全部 `AnimationState.SetAnimation(0, <name>, <loop>)` |
| 名字同时是**配置表键**的 | 14 —— `tbartanimation_animation` 的 24 行 |
| 该表的作用 | 行的 `hideWeapon > 0` ⇒ 播放时隐藏手持武器节点 |

**"何时播"的真正答案是:武器变体由玩家当前装备决定。** `MemberAnimationName.GetIdleAnimationName(weaponId)`
查 `TbEquip_equip` 并 switch `EquipSubType.{Bow,Hammer,Magic,Sword,Spear}` 返回 `"Store/Idle_<class>"`;
`GetSelfIdleAnimationName()` 传入的是**本地玩家自己的装备**(`EquipDataModule.GetWeaponId()`)。因此
`Battle/Attack_{Sword,Bow,Spear,Magic}` 这一族不是装饰,而是**按游戏状态派发**的。这是本案第一次把
表现层(第 7 项)接回游戏状态(第 4 项)。

**方法要点(可复用)**:
1. **按声明类型检索,不要按裸成员名。** 先收集"声明类型确为 Spine 动画类型"的变量(140 个),再搜
   `<var>.<member>`。裸名无用:单是 `Play` 在框架里有 12,121 处命中,几乎全不相干。
2. **三方交叉一致才有分量**:资产(骨架字节,经 Spine 运行时)× 代码(客户端字面量)× 配置(表),
   三个工具读三个文件、彼此无推导;8 个变体名在**三方全部命中**。
3. **不一致的要如实记为残留**:17 个名字(1 个 + 16 个方向名 `HaiYang_/TaiKong_/YinYue_/ZhouNian_`
   × `{You,Zuo}{Shang,Xia}`)既非字面量也非表键,其前缀在 42MB 客户端里 **0 命中** ⇒ 由尚未定位的
   数据解析而来。**不要用相似度补上。**
4. **静态绑定 ≠ 运行观察**:我展示了播放这些名字的代码路径与决定它们的配置行,但**没有**观测到运行的
   游戏播放它们。动态确认仍未取得 —— 且 79 个未解析骨架仍未计入,所以"48/65"是**已读到的 65 个**
   之上的比例,不是全部存在动画之上的比例。

### 追加:阻塞项 2 的前提被证伪 —— "自带 TLS 栈"只是目录名(同日第四次)

收尾报告里一直写着"Blocker 2 未突破:客户端自带 TLS 栈 + 证书固定"。**这个前提从未被检验过。**

原始依据(E-004)是:`files/` 下存在 `com.Tivadar.Best.HTTP.v3/` 目录,于是推断"Best HTTP/3
自带 TLS 栈与证书固定"。E-004 自己都标注了:对 `libil2cpp.so`/`libunity.so` 的 BoringSSL 字符串
扫描**一无所获**,且属弱证据。但结论随后被**历经 11 次 workitem 修订原样传递**,并写进收尾报告
当成定论。**这是本案第四次"由信号推否定、从未复核"**(前三次:目录被删的前提、配置表数字、
APK 覆盖边界),也是**代价最大的一次** —— 因为它"听起来像关于一个敌对系统的实事",而不像一条
关于某个文件夹的备注。

实测三点,任一点即可推翻:

| # | 测量 | 结果 |
|---|---|---|
| 1 | APK 里 23 个 `.so` 有没有自带 TLS 库 | **没有**。`libunity.so` 带的是 Unity **标配** `mbedtls`(x67);`libil2cpp.so` 的 BoringSSL/OpenSSL 标记为 **0** |
| 2 | 有没有**强制执行**的证书固定 | **没有**。全客户端只有一个 `CertificateHandler`,实现是 `ValidateCertificate(...) { return true; }`;固定的公钥/证书哈希**存了却从不读取**;无 `ServicePointManager`,无 `RemoteCertificateValidationCallback` |
| 3 | 真实 API 走哪条传输 | `UnityWebRequest.Put(m_url, body)` + 上述**空校验器**;响应在 `downloadHandler.data` 处**已是明文**,正是 E-018 推导 `id\|len\|protobuf`(`len+6`)的那个位置 |

**一条被抓住的假阳性**:在 42MB 客户端里搜 `pinning` 得 **46 处**命中,看起来是对原结论的
**有力佐证** —— 实际**全部**是 `isSpinning`/`endSpinning`(幸运转盘 UI)。若信这个计数,就会
"确认"一个代码已经推翻的前提。这与"按声明类型限定成员访问"是同一条纪律:**计数不是证据**。

**结论与边界**:阻塞项从"被敌对的 TLS 栈挡住"改为**"尚未尝试,且无已知障碍"**。但**并未因此突破** ——
仍**没有任何 body 被抓到**,只是"纸面上解除了封锁"。另外还存在一条 socket/websocket 传输
(`SocketHost`、`wss://`),**本记录不覆盖**,那是另一个独立的拦截问题。而
`ValidateCertificate => true` 是**对哈希锁定的反编译代码的静态阅读**,不是"观察到用错误证书也能连上"。

**可复用判据**:证据若是**名字**(目录名 / 数字 / 类型计数),结论只能是关于**位置**,不能是关于**能力**。
要落到"能力",必须落到**实现**。
